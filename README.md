### 第一站｜管理基礎｜5.37 書面紀錄之運作程序

**ISMS 作業重點**：開關機、備份還原、批次排程皆有 SOP；異常處理與日誌檢查步驟明確；文件有版本管控並經核准；需要的人員可即時取得

**稽核查核重點**：抽一份 SOP，請值班人員現場演示；比對 SOP 修訂日期與系統異動；新系統上線是否同步交付操作手冊

**常見缺失**：SOP 只存在資深工程師腦袋裡；文件仍寫已退役的舊主機；多年未改版，寫的跟做的不一樣

- **Allan**：第一個，5.37 書面紀錄之運作程序。白話講，就是系統怎麼操作，要寫下來。
- **Allan**：開關機、備份還原、批次排程、異常處理，都要有 SOP，而且要版本管控、經過核准，需要的人拿得到。
- **Allan**：稽核時，我會抽一份 SOP，請值班同仁現場操作一次，看看寫的跟做的是不是一樣。
- **阿拉蕾**：阿拉蕾知道！SOP 只存在資深工程師的腦袋裡，對不對？
- **Allan**：答對！這是最常見的缺失，人一離職，系統就沒人會開機了。還有文件寫的是早就退役的舊主機，也很常見。

### 第一站｜管理基礎｜8.25 安全開發生命週期

**ISMS 作業重點**：訂定 SSDLC 開發規範；各階段設安全檢查關卡（Gate）；開發人員安全程式設計訓練；版控與原始碼存取控制

**稽核查核重點**：抽今年上線專案，從需求追到上線；檢視各 Gate 的審查與簽核紀錄；查開發人員訓練紀錄

**常見缺失**：程序書很漂亮，專案沒照做；改敏捷開發後文件全部消失；小改版一律跳過安全流程

- **Allan**：第二個，8.25 安全開發生命週期，也就是 SSDLC。重點是把安全活動，嵌進開發的每一個階段。
- **Allan**：要訂開發規範，在需求、設計、編碼、測試、上線各設安全關卡，開發人員也要受過安全程式設計訓練。
- **Allan**：查核時，我最喜歡抽一個今年剛上線的專案，從需求一路追到上線，看每一關有沒有留下紀錄。
- **阿拉蕾**：像偵探一樣！叮咚～證據在這裡！
- **Allan**：沒錯。常見缺失是程序書寫得很漂亮，專案卻沒照做；或是改成敏捷開發之後，文件全部消失。
- **Allan**：還有只有大專案才走流程，小改版通通跳過，偏偏出事的，常常就是小改版。

### 第二站｜需求｜8.26 應用系統安全要求事項

**ISMS 作業重點**：需求階段即識別安全需求；鑑別、存取控制、輸入驗證、加密、日誌；納入個資保護與法規要求；線上交易確保完整性與不可否認

**稽核查核重點**：需求規格書是否有安全需求章節；是否依資料分級訂定需求；需求是否經確認簽核

**常見缺失**：一句「依本公司資安規範辦理」帶過；個資欄位沒有遮罩需求；只寫功能需求，沒有安全需求

- **Allan**：進入開發流程，第一步是需求，8.26 應用系統安全要求事項。
- **Allan**：需求階段就要講清楚：身分鑑別、存取控制、輸入驗證、加密、日誌，還有個資保護跟法規要求。
- **Allan**：如果是線上交易，還要考慮交易的完整性、防竄改，以及不可否認性。
- **Allan**：稽核時看需求規格書：有沒有安全需求章節？有沒有依資料分級？需求有沒有確認簽核？
- **阿拉蕾**：如果需求書只寫一句：依本公司資安規範辦理，這樣可以嗎？
- **Allan**：這就是經典缺失！一句話帶過，等於什麼都沒寫。還有個資欄位沒有遮罩需求，上線後畫面直接秀出完整身分證字號。

### 第二站｜架構設計｜8.27 安全系統架構及工程原則

**ISMS 作業重點**：訂定安全工程原則並定期檢視；縱深防禦、最小權限、零信任；預設安全、失效安全；設計審查與威脅建模

**稽核查核重點**：架構圖是否標示網段、安全區域、資料流；設計審查紀錄；原則是否也要求委外廠商遵循

**常見缺失**：架構圖五年沒更新；資料庫直接放在 DMZ；原則文件抄來的，從沒用過

- **Allan**：第二步，架構分析設計，8.27 安全系統架構及工程原則。
- **Allan**：組織要訂安全工程原則，像縱深防禦、最小權限、零信任、預設安全、失效安全，而且要真的用在設計審查。
- **Allan**：稽核時我會請對方拿出系統架構圖，看有沒有標示網段、安全區域跟資料流，再看設計審查紀錄。
- **阿拉蕾**：架構圖阿拉蕾也會畫！畫一坨便便可以嗎？嘿嘿！
- **Allan**：哈哈，不行喔。不過現場常看到的架構圖，五年沒更新，跟實際環境完全對不起來，也差不多了。
- **Allan**：更嚴重的是資料庫直接放在 DMZ，或是工程原則文件是抄來的，從來沒用在任何一次審查。

### 第二站｜程式編寫｜8.28 安全程式設計

**ISMS 作業重點**：安全編碼規範（參考 OWASP Top 10）；輸入驗證、參數化查詢、錯誤處理；禁止將密碼寫死在程式中；源碼檢測、Code Review、SCA／SBOM

**稽核查核重點**：源碼檢測報告高風險是否修補；標為誤判者是否有說明；開源套件清單與已知漏洞追蹤

**常見缺失**：帳密寫在設定檔，還上傳到 Git；使用有已知漏洞的套件（如 Log4j）；高風險全部標成「誤判」

- **Allan**：第三步，程式編寫，8.28 安全程式設計。
- **Allan**：要有安全編碼規範，參考 OWASP Top 10，像輸入驗證、參數化查詢、錯誤處理，絕對不要把密碼寫死在程式裡。
- **Allan**：再搭配源碼檢測、程式碼審查，還有開源套件的管理，也就是 SCA 跟 SBOM。
- **Allan**：查核時，我會看源碼檢測報告：高風險有沒有修？標成誤判的，有沒有說明理由？
- **阿拉蕾**：Log4j！阿拉蕾聽過！那個很恐怖的漏洞！
- **Allan**：對！常見缺失就是用了有已知漏洞的套件卻不知道，帳號密碼寫在設定檔還上傳到 Git，高風險全標成誤判。

### 第二站｜測試驗收｜8.29 開發及驗收中之安全測試

**ISMS 作業重點**：測試計畫納入安全測試；弱點掃描、滲透測試；驗收標準列入安全要求；中高風險修補後複測

**稽核查核重點**：弱掃報告日期 vs 上線日期；中高風險是否複測通過；測試版本是否與正式版本一致

**常見缺失**：先上線、後補掃；修補後沒有複測；報告對應的是舊版本

- **Allan**：第四步，測試與驗收，8.29 開發及驗收中之安全測試。
- **Allan**：測試計畫要包含安全測試，像弱點掃描、滲透測試，驗收標準也要把安全列進去。
- **Allan**：稽核小撇步：把弱掃報告的日期跟上線日期擺在一起看。報告比上線還晚，就是先上線、後補掃。
- **Allan**：另外，中高風險修補之後有沒有複測？測的跟正式環境是不是同一個版本？
- **阿拉蕾**：先上線後補掃，就像阿拉蕾先吃完便當，才說要去洗手！
- **Allan**：形容得太好了！這就是最常見的缺失。另外就是沒有複測，或是測試報告對應的是舊版本。

### 管理案例 1｜趕檔期跳過檢測的電商

1. **趕雙十一**：PM：源碼檢測、弱掃先跳過，上線再補！
2. **SQL Injection**：會員查詢頁被注入，資料庫遭拖庫
3. **十萬筆個資外洩**：依個資法通報、通知當事人、遭主管機關裁罰

> 管理改善：安全測試列為上線必要條件；例外須高階主管書面核准並承擔風險（8.26、8.28、8.29）

- **Allan**：來講一個管理案例。某電商為了趕雙十一檔期，PM 說：源碼檢測跟弱掃先跳過，上線再補。
- **Allan**：結果會員查詢頁有 SQL Injection，被駭客整個拖庫。
- **阿拉蕾**：哇～那後來怎麼辦？
- **Allan**：十萬筆會員個資外洩，要依個資法通報、通知當事人，還被主管機關裁罰，商譽損失更是難以估計。
- **Allan**：管理改善：把安全測試列為上線必要條件，沒有報告就不能上線。真要例外，由高階主管書面核准並承擔風險。

### 第三站｜委外開發｜8.30 委外開發

**ISMS 作業重點**：合約明訂資安要求與保密；智財與原始碼交付、第三方元件授權；漏洞修補保固與稽核權；過程監督並依安全要求驗收

**稽核查核重點**：合約或 RFP 的資安條款；廠商人員保密切結；廠商遠端連線的申請與管控；廠商交付之檢測報告

**常見缺失**：合約沒有任何資安條款；廠商帳號常開，直連正式環境；原始碼未交付，廠商倒了沒人能維護

- **Allan**：接著是橫跨全場的 8.30 委外開發。很多系統都是外包的，但是責任，可沒有外包出去喔。
- **Allan**：合約要寫清楚：保密、智財與原始碼交付、安全測試、漏洞修補保固、第三方元件授權，還有稽核權。過程要監督，最後依安全要求驗收。
- **Allan**：稽核時我會調合約或需求建議書看資安條款，再看廠商人員的保密切結，還有遠端連線怎麼管控。
- **阿拉蕾**：廠商叔叔是不是隨時都可以自己連進來呀？
- **Allan**：這就是常見缺失！廠商帳號常開、直連正式環境；合約沒有資安條款；原始碼沒交付，廠商倒了就沒人能維護。

### 管理案例 2｜廠商帶走的正式資料

1. **為了重現錯誤**：廠商把正式資料庫備份帶回自家測試環境
2. **筆電遺失**：工程師筆電在高鐵上遺失，內含數萬筆病歷
3. **責任在委託方**：對外，醫院仍須負起監督與通報責任

> 管理改善：合約禁止攜出正式資料；測試使用去識別化資料；定期稽核廠商（8.30、8.31、8.33）

- **Allan**：再一個案例。某醫療院所的委外廠商，為了重現錯誤，把正式資料庫備份帶回自家公司的測試環境。
- **Allan**：結果工程師的筆電在高鐵上遺失，裡面有好幾萬筆病歷資料。
- **阿拉蕾**：咦～可是弄丟的是廠商呀？
- **Allan**：對外，責任還是在醫院！委託方要負監督責任。
- **Allan**：改善做法：合約明訂不得攜出正式資料，測試一律使用去識別化資料，並且定期稽核廠商。

### 第四站｜環境區隔｜8.31 開發、測試與運作環境之區隔

**ISMS 作業重點**：三環境以網段、主機、帳號區隔；開發人員原則上無正式環境權限；正式資料不直接用於測試（呼應 8.33）；正式機不留編譯器與開發工具

**稽核查核重點**：正式主機帳號清單有無開發人員；測試資料庫的資料來源；正式機上安裝的軟體清單

**常見缺失**：開發與正式同一台主機；工程師直接在正式機改程式；測試環境用正式資料備份還原

- **Allan**：下一個，8.31 開發、測試與運作環境之區隔。
- **Allan**：三個環境要用網段、主機、帳號權限區隔，開發人員原則上不該有正式環境的權限。
- **Allan**：正式資料也不該直接拿來測試，真的要用，必須去識別化並經過核准，這也呼應 8.33 測試資訊。
- **Allan**：查核時，我會比對正式主機的帳號清單，看有沒有開發人員；也會問：測試資料庫的資料是從哪裡來的？
- **阿拉蕾**：如果開發跟正式，是同一台電腦呢？
- **Allan**：那就是缺失啦！還有工程師直接在正式機上改程式，或是正式機上裝了編譯器和開發工具，都很常見。

### 第四站｜變更管理｜8.32 變更管理

**ISMS 作業重點**：申請 → 影響評估 → 核准 → 測試；實施 → 回復計畫 → 通知 → 文件更新；緊急變更事後補核准、補紀錄；申請、核准、實施職務分離

### 第四站｜系統防護｜8.7 防範惡意軟體

### 第四站｜系統防護｜8.18 具特殊權限公用程式之使用

**ISMS 作業重點**：識別可繞過控制的工具；DB 管理、遠端執行、封包側錄工具；限制使用並經授權；保留使用紀錄，不需要即移除

**稽核查核重點**：正式主機已安裝工具清單；可執行工具的人員與權限；工具使用紀錄

**常見缺失**：DB 工具人人能開，直接改資料；沒有任何使用紀錄；封包工具裝了就沒移除

- **Allan**：8.18 具特殊權限公用程式之使用，指的是可以繞過系統或應用程式控制的工具。
- **Allan**：像資料庫管理工具、遠端執行工具、封包側錄工具，都要限制使用、經過授權，並保留紀錄，不需要的就移除。
- **Allan**：查核時，我會看正式主機上裝了哪些工具、誰可以執行、有沒有使用紀錄。

### 第四站｜系統防護｜8.34 稽核測試期間資訊系統之保護
